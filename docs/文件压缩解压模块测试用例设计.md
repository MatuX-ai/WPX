# 文件压缩解压模块测试用例设计

## 范围与约定

- **被测模块**：
  - `electron/zip-ipc.js` — 主进程 IPC handler（zip:compress / zip:extract / zip:list / zip:cancel / zip:pick-* / isArchiveFile）
  - `electron/zip-service.js` — 7za 调用封装（压缩/解压/列表/取消/进度/错误恢复/路径安全校验）
  - `wpx-app/src/stores/zip.js` — Pinia store（操作状态、并发上限、取消、进度订阅）
  - `wpx-app/src/utils/zipApi.js` — 渲染进程 API 封装（参数校验、响应解析、环境检测）
- **测试框架**：Vitest。主进程测试用 `createRequire` 加载 CommonJS 模块；渲染进程测试用 `@vue/test-utils` + `createPinia`。
- **依赖**：`zip-service` 集成用例依赖 `resources/bin/7za.exe`（Windows），无 7za 时按现有约定整体 skip（参考 `electron/__tests__/zip-service.test.js`）。
- **Mock 策略**：IPC 用例 mock `ipcMain.handle` 与 `electron` 的 `BrowserWindow.fromWebContents`；`zip-service` 单元用例 mock `child_process.spawn` / `fs.existsSync` / `./7za-path`；store 用例 mock `@/utils/zipApi`。
- **优先级**：P0 核心流程（extract / compress 主链路）→ P1 错误处理 → P2 边界（空文件 / 大文件 / 特殊字符文件名 / 编码）。

## 待确认/补充项

1. **超时机制**：`stores/zip.js` 与 `zip-service.js` 当前均无操作超时逻辑，`ZIP-STORE-010` 仅锁定"挂起时状态一致"。若产品要求超时强制取消，需先实现超时逻辑再补用例。

3. **并发上限**：当前仅限制已完成操作数量（`MAX_ZIP_PROGRESS_ITEMS = 3`），未限制同时运行的压缩任务数；若需并发执行上限，需补充设计。
